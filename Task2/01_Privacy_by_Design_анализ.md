# Анализ рисков конфиденциальности и проектирование по Privacy by Design

## 1. Назначение

Документ содержит анализ рисков конфиденциальности в состоянии As-Is и описание того, 
как новые архитектурные блоки предупреждают эти риски на этапе проектирования. 
Опирается на проблемные зоны из `Task1/04_Проблемные_зоны.md` и меры из `Task1/07_Инструменты_и_меры.md`.

Подход — Privacy by Design (PbD) в 7 принципах. Задача: не «закрыть дыры после инцидента», 
а сделать нарушение конфиденциальности технически невозможным или сразу заметным.

## 2. Семь принципов PbD в контексте «Медикаменте»

| Принцип | Что означает для «Медикаменте» | Проблемная зона As-Is |
|---|---|---|
| Proactive not reactive | Предупреждать утечки, а не расследовать их | Нет аудита, нет алертинга (3.2) |
| Privacy as default | Минимальные права по умолчанию | Общий диск, доступ у всех (3.1, 4.1) |
| Privacy embedded into design | Защита встроена в архитектуру, а не «прикручена» | Excel, файлы на шаре (3.1) |
| Full functionality (positive-sum) | Безопасность без потери функций | BI/ML без обезличивания (4.5) |
| End-to-end security | Защита на всём пути данных | Нет шифрования, неформальные каналы (3.1, 3.3) |
| Visibility and transparency | Аудит и прозрачность для субъекта и регулятора | Нет согласий, нет аудита (3.2, 3.4) |
| Respect for user privacy | Права субъекта: доступ, удаление, прекращение обработки | Нет процедуры уничтожения (5.3) |

## 3. Новые блоки архитектуры и закрываемые риски

| Блок | Назначение | Закрывает зоны | Принципы PbD |
|---|---|---|---|
| **API Gateway** | Единая точка входа, валидация контрактов, скрытие PII в ответах, защита от IDOR | 3.3 (неформальный обмен), 4.1 | Privacy as default, end-to-end security |
| **Identity & Access Service (IAM + OPA)** | Аутентификация, RBAC/ABAC по тегам, проверка контекста | 4.1 (нет разграничения) | Privacy as default, visibility |
| **Consent & Privacy Service** | Сбор согласий, реализация прав субъекта (доступ, удаление, прекращение) | 3.4 (нет согласий), 5.3 (нет уничтожения) | Respect for user privacy, proactive |
| **Data Classification & Tagging Service** | Присвоение тегов PII/PHI/payment и т.д., автоматическая защита по тегам | 3.1, 4.1, 4.5 | Embedded privacy, full functionality |
| **Audit & Monitoring Service** | Журналирование доступа, алертинг аномалий | 3.2 (нет аудита) | Visibility, proactive |
| **Encryption & Key Management (Vault)** | Шифрование at rest, ротация ключей, секреты | 3.1 (нет шифрования) | End-to-end security |
| **Data Lake с Privacy Layer** | BI/ML/AI на обезличенных данных | 4.5 (нет аналитики с PbD) | Full functionality, privacy as default |
| **Client & Staff Portal** | Самостоятельная запись, ЛК пациента, рабочие места | 3.4, 4.1 | Proactive, embedded |

## 4. Механизмы предупреждения рисков (до реализации)

1. **Политика по умолчанию (default deny).** IAM + OPA: доступ к любому полю с тегом `pii`/`phi`
запрещён, пока роль и контекст явно не разрешают. Это делает случайное раскрытие невозможным.
2. **Тегирование на входе.** Data Classification Service присваивает тег каждому полю при записи.
Запись без тега в продакшн не проходит. Это закрывает «слепые зоны» из Task1.
3. **Скрытие PII в API.** API Gateway возвращает только те поля, которые разрешены контрактом и ролью;
остальные маскируются. Один пациент не может запросить данные другого (проверка `subject_id` в контексте).
4. **Согласие как предусловие.** Consent Service блокирует обработку, если согласия нет или оно отозвано.
Это встраивает принцип в поток, а не в регламент.
5. **Аудит и алертинг.** Audit Service фиксирует каждое обращение к тегированным данным; аномалии 
(массовая выгрузка, доступ вне рабочих часов) вызывают алерт.
6. **Шифрование по умолчанию.** Vault управляет ключами; объектное хранилище и БД шифруют данные at rest
без участия разработчика.
7. **Обезличивание на входе в аналитику.** Data Lake получает данные только после обработки Privacy Layer
(псевдонимизация, k-анонимность).
8. **Удаление по запросу.** Consent & Privacy Service инициирует каскадное удаление/обезличивание
во всех системах по `subject_id`.

## 5. Связь с бизнес-целями

- **Пятикратный рост и филиалы:** новые блоки (IAM, API Gateway, Audit) масштабируются горизонтально в Kubernetes.
- **Портал и мобильное приложение:** Portal + API Gateway + IAM + Consent Service дают безопасную запись и ЛК.
- **BI/ML/AI:** Data Lake с Privacy Layer обеспечивает аналитику без раскрытия PII.
- **Интеграция с лабораторией:** API Gateway + OPA валидируют контракты и исключают неформальные каналы.

## 6. Выводы

- Все критические зоны из Task1 закрываются конкретными блоками, а не «общими мерами».
- PbD реализован на уровне архитектуры: default deny, теги на входе, согласие как предусловие, аудит,
шифрование, обезличивание.
- Механизмы предупреждают риски до реализации: нарушение становится либо невозможным, либо сразу заметным.
