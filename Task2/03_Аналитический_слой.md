# Аналитический слой с Privacy by Design

## 1. Назначение

Документ описывает целевой аналитический слой (BI/ML/AI) и то, как он реализует Privacy by Design.
Опирается на цель бизнеса №2 (озеро данных из Excel) и проблемную зону 4.5 (нет Data Lineage).

## 2. Проблема As-Is

- Данные для аналитики лежат в Excel (`Patients`, `RegistryByDate`, `Journal-Doctor-FIO 1`) и файлах на общем диске.
- Нет обезличивания: аналитик видит PII и PHI напрямую.
- Нет Data Lineage: невозможно понять, откуда пришли данные и как они преобразованы.
- Нет контроля доступа: аналитик может выгрузить всё.

## 3. Целевая архитектура аналитического слоя

[Доменные сервисы] → [Data Classification & Tagging] → [Privacy Layer] → [Data Lake] → [ClickHouse] → [BI/ML Services]

### 3.1. Источники
Доменные сервисы (Appointment, Medical Records, Billing, Laboratory) пишут данные в свои БД.
Каждое поле уже имеет тег (`pii`, `phi`, `payment`, `commercial`).

### 3.2. Privacy Layer (ключевой блок)
На входе в Data Lake данные проходят обработку:
- **Псевдонимизация**: `subject_id` заменяется на устойчивый псевдоним (детерминированная маскировка),
связь хранится в защищённом реестре.
- **k-анонимность**: для агрегированных наборов гарантируется, что в каждой группе не менее k записей
— реидентификация невозможна.
- **Обобщение**: дата рождения → возрастная группа; адрес → регион.
- **Удаление прямых идентификаторов**: ФИО, телефон, email не попадают в озеро.
- **Теги сохраняются**: аналитик видит, что поле обезличено, и не может его «раскрыть».

### 3.3. Data Lake
- Хранит только обезличенные данные.
- Теги и метаданные (Data Lineage) фиксируют происхождение и преобразования.
- Доступ через сервисный аккаунт с ограниченными правами.

### 3.4. ClickHouse (Analytics)
- Хранилище для быстрых отчётов.
- Только агрегированные и обезличенные данные.
- Отдельный кластер, изолированный от продакшн-БД.

### 3.5. BI & ML Services
- Отчёты (P&L, ABC-анализ) — на обезличенных данных.
- Обучение ML-моделей — на обезличенных данных.
- LLM — только на данных без PII/PHI.
- Запрет реидентификации: попытка джойна с продакшн-БД блокируется политикой.

## 4. Принципы PbD в аналитическом слое

| Принцип | Реализация |
|---|---|
| Full functionality | Аналитика работает в полном объёме, но на обезличенных данных |
| Privacy as default | По умолчанию в озеро попадают только обезличенные данные |
| End-to-end security | Шифрование на всех этапах, TLS между сервисами |
| Visibility | Data Lineage: видно, откуда данные и как преобразованы |
| Respect for user privacy | Если субъект отозвал согласие — его данные удаляются из озера |

## 5. Инструменты

| Задача | Инструмент | Обоснование |
|---|---|---|
| Тегирование | OpenMetadata / DataHub | Open-source, интеграция с Postgres, ClickHouse |
| Псевдонимизация | Самописный сервис или Apache NiFi | Гибкость, контроль |
| Data Lake | MinIO / S3-совместимое | On-prem, 152-ФЗ |
| Аналитика | ClickHouse | Уже в стеке техдира |
| BI | Superset / Metabase | Open-source |
| ML | Python + Jupyter (в изолированной среде) | Стандарт |
| Аудит | Elastic | Уже в стеке |
| Политики | OPA | Политики как код |

## 6. Data Lineage в аналитике

- Каждый набор данных в озере имеет метаданные: источник, преобразования, теги, владелец.
- OpenMetadata строит граф: `Medical Records DB → Privacy Layer → Data Lake → ClickHouse → Отчёт`.
- При обнаружении ошибки видно, на каком этапе она возникла.
- При запросе субъекта «удалите мои данные» — Data Lineage показывает все места, где они есть,
и Consent Service инициирует каскадное удаление.

## 7. Выводы

- Аналитический слой изолирован: BI/ML не видит PII/PHI.
- Privacy Layer — единственный вход в озеро, обойти его нельзя.
- Data Lineage обеспечивает прозрачность и выполнение прав субъекта.
- Решение соответствует 152-ФЗ (данные on-prem, обезличивание) и целям бизнеса (BI/ML/AI).
